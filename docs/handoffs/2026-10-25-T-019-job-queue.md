## What changed

New package `prototype/server/app/jobs/`:

- `queue.py`
  - SQLite tables `jobs` and `job_submissions` on the app's existing autocommit connection.
  - Job row: kind, unique idempotency key, log/submission, priority, provider backend, JSON payload, state, attempts, `run_after`, lease token/expiry/worker, result, error label, created/updated/finished times.
  - **Idempotent enqueue:** the unique key returns the stored job, including after a restart. The same key with different kind/log/submission/priority/backend/payload raises `IdempotencyConflict`. `run_after` is not part of the comparison.
  - **Claim and lease:** one row is selected and leased inside `BEGIN IMMEDIATE` with a random token; `attempts` increments at claim. Expired running jobs are returned to `queued` at the start of every claim and by `recover_expired()`.
  - **Fencing:** `complete`, `fail`, `renew` and `cancel` require the current token and `running` state. A recovered, reclaimed or cancelled job raises `LeaseLost` and publishes nothing.
  - **Provider bound:** jobs whose `backend` is set are limited to `max_per_backend` (default 4) running jobs for that backend. `backend=None` jobs (parsing, replay, receipt assembly) take no provider slot. Other backends use their own slots.
  - **Fairness:** same-priority jobs rotate by submission; ties go to the earliest first enqueue. `submission_id` defaults to `log_id`; jobs with neither share one system bucket.
  - **Priority:** `PRIORITY_NORMAL = 0` and `PRIORITY_MAPPER = 100` (reserved, lowest). The mapper's skip rule, one-job-per-log rule and 40-call cap are **not** implemented; they belong to M4m.
  - **Retries:** retryable failure returns the job to `queued` after 1, 4, 16 minutes, then repeats the last delay. Non-retryable failure is terminal. There is no attempt limit (see PD-1).
  - **Cancellation:** `cancel_by_log(log_id, kinds=None, reason=..., conn=None)` cancels queued and running jobs in one update and fences the running lease. `conn=` joins a caller-owned transaction.
  - `recover_expired`, `get`, `stats` (state counts, running per backend).
- `runner.py`
  - `JobRunner(queue, handlers, worker_id=...)`; handlers receive the claimed `Job` and return a dict or raise `RetryableJobError` / `PermanentJobError`.
  - Handlers run after the claim transaction commits and before the completion transaction starts. An unexpected exception is terminal and only its class name is stored (never its message).
  - `run_once()`, `run_pending(max_concurrent=8)` (threads; the queue cap still bounds providers), `run_until_idle(max_jobs=None)`.
- `__init__.py` exports the public API and documents the T-020/T-021 integration surface.

New `prototype/server/tests/test_jobs_queue.py` (37 tests).

`docs/TASKS.md`: only the T-019 row (Owner `worker-T-019`, then `review`).

## API for T-020 and T-021

```python
queue = JobQueue(event_service.db, clock=clock, lease_seconds=300,
                 max_per_backend=4, retry_delays_minutes=(1, 4, 16))

job = queue.enqueue(kind, idempotency_key, log_id=..., submission_id=None,
                    priority=PRIORITY_NORMAL, backend=None, payload={},
                    run_after=None, conn=None)
claimed = queue.claim(worker_id=...)        # Job | None
queue.renew(claimed)                         # long handlers
queue.complete(claimed, result_dict)         # raises LeaseLost if fenced
queue.fail(claimed, error_kind="timeout", retryable=True)
queue.cancel_by_log(log_id, kinds=None, reason="record.withdrawn", conn=None)
queue.recover_expired(); queue.get(job_id); queue.stats()
```

- **T-020:** enqueue compile/L3/question work with stable keys and pass `event_service.db` so submit and enqueue can share one caller-owned transaction (`conn=`). Set `backend` on every job that calls a provider. Enqueue at submit so first-enqueue order matches submit order.
- **T-021:** call `cancel_by_log(..., conn=event_service.db)` inside the `record.withdrawn` transaction. Running handlers still need to read the withdrawn state before writing outside the queue (D10); the queue rejects their completion.
- Connection contract: the connection must be autocommit (`isolation_level=None`, as `EventStore` creates it). Passing `conn=` means the caller owns the transaction and serialisation.

## Proposed decisions (the checker takes these to the founder; nothing here is decided)

1. **Retry terminal behaviour (required by the ticket).** D23 gives 1/4/16 minutes "then wait for the D7 cap" but does not say what ends retries. This queue repeats the 16-minute delay with no attempt limit and leaves the job `queued`; the release cap and any terminal decision remain with T-021. *Recommend:* accept; alternatively T-021 adds a per-submission deadline and cancels or marks the job terminal at the cap.
2. **One running job = one provider slot.** The queue bounds concurrent jobs per backend, not individual calls inside a handler, because calls happen inside `app/llm.py`. *Recommend:* accept the conservative bound and require T-020 handlers to make at most one concurrent provider call per job.
3. **Lease length and renewal.** D23 does not name a lease duration. The default is 300 seconds with `renew()` for long work; completion is fenced by the token, not by the clock alone. *Recommend:* accept; revisit if compile handlers routinely exceed five minutes.
4. **Submission order.** `submission_id` defaults to `log_id`, and round-robin uses the order in which each submission's first job was enqueued. T-020 must enqueue at submit for "earliest submit first" to mean submit order. Jobs with neither id share one system bucket. *Recommend:* accept.
5. **Priority values and mapper scope.** `PRIORITY_NORMAL = 0`, `PRIORITY_MAPPER = 100`; only ordering is implemented. The < 30-word skip, one queued job per log, 40-call cap and cancellation at submit stay in M4m/T-020. *Recommend:* accept.
6. **Cancellation of a running job.** Marking it cancelled immediately and fencing its completion is the queue's part of D10. The handler itself keeps running; the withdrawn check before any outside write belongs to T-021/storage. *Recommend:* accept.
7. **Unexpected handler exception.** It becomes a terminal `failed` job with only the exception class name stored; transient errors must raise `RetryableJobError` explicitly. *Recommend:* accept; never store an exception message, which could contain student text.
